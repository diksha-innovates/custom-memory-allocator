# Interview Questions — custom-memory-allocator

All answers are written in my own voice, grounded in this codebase. File/function references point at real locations as of this build.

## A. Pitches and architecture walkthrough

**1. Give me the 60-second pitch.**
This project is two from-scratch allocation strategies — a bump arena allocator and an explicit free-list allocator with boundary-tag coalescing — behind one facade API (`MemoryAllocator`), plus a `std::pmr::memory_resource` adapter so either one can back a standard container. Both report failures (OOM, double-free, corruption) by value instead of crashing or throwing, which made them directly testable: 25 GoogleTest cases include a 5000-iteration randomized property test asserting no two live allocations ever overlap. I benchmarked both against `malloc`/`new` on three fixed-seed workloads and found p50 latency roughly 2x better for both custom strategies, with the more interesting finding being a methodology bug I caught myself: my own debug invariant-checking assertion was making `free_list_first_fit` look 1000x slower than it actually is, because it's O(n) and I was benchmarking a Debug build.

**2. Give me the 3-minute version.**
Start with the two strategies. `ArenaAllocator` (`src/arena_allocator.cpp`) is the simple case: one buffer, one offset, `allocate()` computes the next aligned address directly from the absolute pointer value (not just the offset) so it supports any power-of-two alignment, bumps the offset, and returns. `deallocate()` is a documented no-op — a bump allocator fundamentally cannot reclaim one allocation out of many — only `reset()` reclaims everything at once.
`FreeListAllocator` (`src/free_list_allocator.cpp`) is the substantial piece: every block, free or allocated, has a header and footer (the boundary-tag technique), and `BlockHeader` is declared `alignas(64)`, which does two things simultaneously — forces every block's address to 64-byte alignment, and forces `sizeof(BlockHeader)` itself to be a multiple of 64, so the payload pointer right after the header is automatically aligned without any per-allocation bookkeeping. `allocate()` rounds the request up to a 64-byte-granular block size, finds a fit (first-fit or best-fit, same free list, different scan policy), splits off a remainder if it's worth keeping, and hands back the payload. `deallocate()` reads the header via `ptr - sizeof(BlockHeader)`, checks a magic number (catching double-free and most corruption), then coalesces forward and backward with physically-adjacent free blocks using the boundary tags before reinserting into the free list.
`MemoryAllocator` (`include/allocator/memory_allocator.hpp`) is the facade — it owns a `unique_ptr<AllocatorStrategy>` and forwards every call, so swapping strategies is a one-line change. `PmrAdapter` bridges this facade's "never throw, return nullptr" contract to `std::pmr::memory_resource`'s "must throw `std::bad_alloc`" contract — the one place that translation happens. Everything is verified by a `check_invariants()` structural walker, asserted after every mutation in debug builds, and by a benchmark CLI that replays identical fixed-seed workloads across all five allocators (malloc, new, arena, free-list first-fit, free-list best-fit) to get a fair comparison.

**3. Walk me through the architecture as if I've never seen this repo.**
Four pieces, bottom-up: (1) `AllocatorStrategy` (`include/allocator/allocator_strategy.hpp`) — the pure interface, allocate/deallocate/reset/stats/owns. (2) Two implementations of it: `ArenaAllocator` and `FreeListAllocator`, each in its own header+source pair, neither aware of the other. (3) `MemoryAllocator` — the facade applications actually hold, owning one strategy via `unique_ptr<AllocatorStrategy>`. (4) `PmrAdapter` — an optional wrapper around a `MemoryAllocator` for code that wants to use standard `std::pmr` containers instead of calling `allocate()`/`deallocate()` directly. `benchmarks/bench_main.cpp` and `tests/unit/*.cpp` are both pure consumers of layers 2-4, nothing in the allocator code depends on either.

## B. Module deep-dives

**4. Why does `ArenaAllocator::allocate()` align the absolute address, not just the offset?**
Because `storage_.get()` (the buffer's base address) is not guaranteed to itself be aligned beyond whatever `operator new[]` gives a `std::byte[]` (typically `alignof(std::max_align_t)`, often 16). If I only aligned the *offset* (e.g. rounded `offset_` up to a multiple of `alignment`), the resulting address `base + aligned_offset` would only actually be aligned to `alignment` if `base` itself already was — which isn't guaranteed for alignments larger than the base's own alignment. Computing `(addr + (alignment-1)) & ~(alignment-1)` on the real pointer value sidesteps that assumption entirely and is correct for any alignment, which is exactly why `ArenaAllocator` (unlike `FreeListAllocator`) has no upper cap on supported alignment — it's tested up to 512 bytes in `test_arena_allocator.cpp`.

**5. Why does `FreeListAllocator` cap alignment at 64 bytes while `ArenaAllocator` doesn't?**
`ArenaAllocator` aligns fresh, per-call, directly against the absolute address — there's no structural constraint to work around. `FreeListAllocator` instead gets alignment "for free" structurally: every block's address is a multiple of `kMaxSupportedAlignment` by construction (arena base rounded up to it, `BlockHeader` padded via `alignas()` to a multiple of it, every block size rounded up to a multiple of it), so the payload pointer is automatically aligned with zero extra bookkeeping — but only up to whatever that one fixed constant is. Supporting a larger alignment on demand would mean either raising that constant everywhere (wasting space on every block, even ones that never need it) or adding a per-allocation back-pointer trick (real overhead, more code, an extra indirection on every deallocate). I picked a fixed, generous cap and documented the trade-off instead.

**6. Walk me through exactly what `alignas(FreeListAllocator::kMaxSupportedAlignment)` does to `BlockHeader`, mechanically.**
Two things: it sets the type's alignment *requirement* to 64 (so any `BlockHeader` object, or array of them, is placed at a 64-aligned address by whoever allocates it), and as a consequence of C++'s rule that `sizeof(T)` must be a multiple of `alignof(T)` (so that arrays of `T` keep every element aligned), the compiler pads the struct's size up to the next multiple of 64 even though the actual fields (`size_t` + `uint32_t` + `bool` + two pointers) add up to far less. I rely on *both* effects: the first is what makes block addresses land on 64-byte boundaries (combined with the arena base being rounded the same way and block sizes being rounded the same way), and the second is what makes `block_start + sizeof(BlockHeader)` — the payload address — also land on a 64-byte boundary.

**7. What exactly is a "boundary tag" and where is it in this code?**
A boundary tag is metadata duplicated at *both* ends of a memory block — here, `BlockHeader` at the start and `BlockFooter` at the end, both storing `block_size`. The footer's purpose is specifically to let `prev_physical()` (`free_list_allocator.cpp`) find the block immediately before a given one: it reads the footer at `block_start - sizeof(BlockFooter)`, which tells it that previous block's `block_size`, and therefore its start address (`block_start - footer->block_size`). Without a footer, there would be no way to walk backward through physically-adjacent blocks at all — only forward, via each header's own `block_size`.

**8. Why is `deallocate()`'s double-free / corruption detection based on a magic number rather than, say, a separate "is this pointer live" set?**
A magic number is O(1) and lives right where the check needs it (the block header, already being read to find the block's size for coalescing) — no separate data structure to keep in sync with every allocate/deallocate. The trade-off: it's probabilistic, not absolute — in principle, a `CorruptedHeader` could coincidentally contain exactly `kFreeMagic`'s bit pattern through unrelated memory corruption and be misdiagnosed as `DoubleFree` rather than general corruption. Given the two magic constants (`0xF4EEF4EEu`, `0xA110CA11u`) are chosen to be visually/numerically distinctive and nothing in this codebase ever writes arbitrary attacker-controlled bytes into a header, I judged this an acceptable, standard trade-off (the same one most real allocators with any corruption detection at all make) rather than paying for a separate liveness-tracking structure.

**9. What does `split_block()` do when the remainder would be too small to be its own block?**
It does nothing — leaves `block->block_size` as the full original size, meaning the caller gets a block larger than it asked for (internal fragmentation, documented in the README). The threshold is `round_up(sizeof(BlockHeader) + sizeof(BlockFooter), kMaxSupportedAlignment)` — if the leftover couldn't even hold an *empty* block's own header+footer, there would be nothing legitimate to put there anyway (not even zero payload bytes, since that's still less than the overhead itself), so keeping it unsplit is the only correct option, not just a convenient one.

**10. Walk me through `deallocate()`'s coalescing order — why forward, then backward, not the other way or simultaneously?**
Forward is checked first purely because it's checked against `merged`, which starts out *as* the block being freed (its address doesn't change yet); backward coalescing reassigns `merged = prev`, changing which address represents "the current merged block" from that point on. Doing it in the opposite order would require either finding `prev` before updating `merged`'s size (which the code does do, in fact — `prev = prev_physical(merged)` runs using `merged`'s *original* address before any reassignment) or recomputing addresses twice. The order here (forward merge into `merged`, then check backward from `merged`'s *original* address, then reassign if backward also merges) handles the three-way merge (prev-free, this-just-freed, next-free, all three becoming one block) correctly in a single pass, which the `FreeingAllAllocationsCoalescesBackToOneRegion` test exercises directly.

**11. Why does `MemoryAllocator::create<T>()` not support arrays?**
Because `::operator new[]`'s array support relies on compiler-inserted "array cookies" (hidden bookkeeping before the array, usually the element count) so `delete[]` knows how many destructors to run — this allocator has no equivalent mechanism, and inventing one would mean either reserving extra space in every block for a cookie nobody but arrays need, or detecting arrays specially. Simpler, and equally correct: a caller needing an array calls `allocate()` for the raw bytes and placement-news each element itself, which is explicit about ownership and destructor-running responsibility rather than hiding it behind a convenience method that can't fully replicate `new[]`/`delete[]`'s contract.

**12. Why does `PmrAdapter::do_deallocate()` only `assert()` on a non-Ok result instead of doing something more robust?**
Because `std::pmr::memory_resource::do_deallocate()` returns `void` and the standard does not permit it to throw — there is no channel back to the caller to report "that pointer was already freed" even if I wanted one. A well-behaved `std::pmr` container only ever passes back exactly what it got from `do_allocate()` on this exact resource, so a non-Ok result here would mean either a bug in the standard library's container implementation or memory corruption elsewhere — genuinely exceptional circumstances where a debug-build crash (via `assert`) is more useful than silent continuation, and a Release build's silent ignore (documented in the README) is the best available option given the interface's constraints.

## C. Design trade-offs — "why not X?"

**13. Why a facade + strategy interface instead of just two unrelated classes with similar method names (duck typing via templates)?**
A template-based approach (calling code templated on the allocator type) avoids the one virtual call per `allocate()`/`deallocate()`, but it means the strategy choice leaks into every type that uses an allocator — `std::vector<int, MyTemplatedAllocator<ArenaAllocator>>` is a different type from the free-list version, so you can't swap strategies without recompiling (or re-templating) every caller. The spec explicitly asks for a facade that separates the API from the strategy; a runtime-polymorphic interface is the direct way to get "swap the strategy, callers don't change," and the benchmark confirms the virtual-call cost doesn't erase the win over `malloc` anyway.

**14. Why not just use `posix_memalign`/`std::aligned_alloc` as the arena's backing storage to guarantee a stricter base alignment up front, instead of over-allocating and rounding?**
For `FreeListAllocator` specifically, I did effectively this (`raw_size = capacity_bytes + kMaxSupportedAlignment`, then round the base pointer up) rather than relying on a platform-specific aligned-allocation API, so the exact same code path works identically on macOS and Linux without `#ifdef`s for different aligned-allocation APIs (`posix_memalign` vs `std::aligned_alloc`'s size-must-be-a-multiple-of-alignment requirement, which doesn't match an arbitrary `capacity_bytes`). The over-allocate-and-round technique is simpler and perfectly portable at the cost of up to `kMaxSupportedAlignment - 1` wasted bytes, which is negligible next to any realistic arena size.

**15. Why first-fit AND best-fit, rather than picking the one that's "better" and only implementing that?**
Because neither is strictly better — that's the actual, measured point of `FirstFitPicksTheMostRecentlyFreedEligibleBlockBestFitPicksTheSmallest` and the benchmark's "mixed" workload result (first-fit noticeably slower there than best-fit, the opposite of first-fit's usual reputation for being cheaper per call). Implementing only one would have meant asserting a general claim ("X is better") without being able to demonstrate the actual trade-off with real data, which is exactly the kind of invented-authority claim this project's rules explicitly forbid.

**16. Why does the benchmark track "currently reserved" bytes for malloc/new via a manual side-table (`unordered_map<void*, size_t>`) instead of querying process RSS?**
Process RSS (resident set size) reflects OS-level paging decisions (when pages are actually committed/reclaimed), which is a real and interesting number but a different one from "how many bytes does the application currently believe it owns," which is what `FreeListAllocator::stats().bytes_in_use` reports and what I wanted a fair, apples-to-apples comparison against. `malloc`/`new` don't expose "how big was this block" given only a pointer, so the side-table is the only way to reconstruct the same "live requested bytes" number for them that the custom allocators track natively. I actually got this wrong on the first pass (the `reserved` counter only incremented, never decremented on free) and caught it myself before trusting the numbers — see the debugging stories section.

**17. Why is `check_invariants()` O(n) instead of maintaining running counters that could verify incrementally in O(1)?**
Because the entire point of an invariant checker is to catch bugs in the code that maintains those very running counters — if `check_invariants()` trusted an incrementally-maintained "total bytes" counter instead of re-deriving it by walking every block, a bug that corrupted that counter would be invisible to the checker. Its value comes specifically from being an independent, from-scratch re-derivation of every fact it checks, which is why it's O(n) and deliberately kept out of the release hot path (gated by `assert`, compiled out under `NDEBUG`).

## D. C++ language questions the code touches

**18. Where does this project rely on `alignas`, and what would break if it were removed from `BlockHeader`?**
`struct alignas(FreeListAllocator::kMaxSupportedAlignment) FreeListAllocator::BlockHeader` in `free_list_allocator.cpp`. Removing it would mean `sizeof(BlockHeader)` reverts to its natural size (fields packed per ordinary alignment rules, likely 40 bytes: 8+4+1+3-padding+8+8 or similar), which is not a multiple of 64 — so `block_start + sizeof(BlockHeader)` would no longer reliably be 64-aligned even if `block_start` itself still were, breaking the entire "alignment is free" guarantee `allocate()` depends on. Every alignment test above whatever `sizeof(BlockHeader)` happened to reduce to would start failing intermittently depending on which free block was chosen.

**19. Where does this project use `reinterpret_cast`, and why not `static_cast` or `std::bit_cast`?**
Extensively in `free_list_allocator.cpp` — converting between `std::byte*`/`void*` and `BlockHeader*`/`BlockFooter*`, and between pointers and `std::uintptr_t` for alignment arithmetic. `reinterpret_cast` is the correct tool specifically because these are *type-punning* conversions between unrelated pointer types pointing at the same raw memory, which `static_cast` does not permit (it only allows casts along an actual type relationship, e.g. up/down a class hierarchy) and `std::bit_cast` doesn't fit either (it copies bytes into a new object of the target type, which is wrong here — I want to *reinterpret the existing bytes in place*, not copy them into a temporary).

**20. Is interpreting raw, uninitialized (or formerly-differently-typed) memory as a `BlockHeader*` via `reinterpret_cast` technically undefined behavior?**
Strictly, under the C++ object model, accessing memory through a pointer of a type that wasn't used to create an object there is in a legally murky area that the standard has tightened over successive revisions (`std::launder`, implicit-lifetime types, etc.) — this is a widely-acknowledged "necessary evil" shared by essentially every custom allocator, including ones in major production codebases, because the alternative (placement-new-ing a real `BlockHeader` object at every address before touching it, and explicitly ending its lifetime before reusing the bytes) is far more verbose and not what real-world allocator code actually does in practice. I did not add `std::launder` or placement-new ceremony here; I'm flagging this honestly as a known, common, not-fully-standard-pure technique rather than claiming pedantic correctness I haven't verified — and it's exactly the kind of thing ASan+UBSan (both run clean on this project) are good at catching the *practical* consequences of, even if they can't certify strict standards conformance.

**21. Why does `AllocatorStrategy` use virtual functions instead of, say, `std::variant<ArenaAllocator, FreeListAllocator>` with `std::visit`?**
A `std::variant`-based design would avoid the vtable indirection and could be slightly faster, but it would mean `MemoryAllocator` (or anything holding the variant) would need to know the full, closed set of strategy types at compile time — adding a third strategy later would mean touching the variant's type list everywhere it's named. A virtual interface keeps the set of strategies open (anyone can write a new `AllocatorStrategy` subclass without modifying `MemoryAllocator` at all), which matches "facade separating API from strategy" more directly — the facade shouldn't need to know how many strategies exist.

**22. Where are move semantics used (or deliberately not used) in this codebase?**
`MemoryAllocator` is move-constructible/move-assignable (`= default` for both, since it just holds one `unique_ptr`), so ownership of a configured allocator can be transferred — e.g. returned from a factory function — without copying. `ArenaAllocator` and `FreeListAllocator` are explicitly non-movable (deleted move constructor/assignment) because a `FreeListAllocator` in particular has internal pointers (`free_list_head_`, every block's `prev_free`/`next_free`) that point into its own `raw_storage_` buffer — moving the object wouldn't move those pointer *targets*, so a naive member-wise move would either dangle (if storage is moved too, the internal pointers are still fine since they're offsets into the same buffer... actually they'd still be valid since `raw_storage_` is a `unique_ptr` whose moved-to value points at the same heap memory) or just adds complexity for a use case (moving a live allocator mid-use) this project never needed - I disabled it explicitly rather than leave it accidentally-working-by-luck.

**23. Why does `FreeListAllocator`'s constructor call `reset()` instead of duplicating its block-initialization logic inline?**
Because "the arena is uninitialized" and "the arena has just been reset" are genuinely the same state (one giant free block spanning the whole usable arena) — writing that logic once in `reset()` and having the constructor call it (`FreeListAllocator::FreeListAllocator(...) { ...; reset(); }`) means there is exactly one place that can get "what does an empty arena look like" wrong, instead of two copies that could silently drift apart after a future edit to one but not the other.

**24. What's the complexity and allocation behavior of `find_fit()` under best-fit specifically, and why does it have to look at every block?**
O(k) in the number of free blocks, always — unlike first-fit, which can return as soon as it finds any fit, best-fit cannot know a candidate is "the smallest that fits" without having compared it against every other candidate, so it must walk the entire free list every time, even if the very first block it sees would have been a perfectly adequate first-fit answer. This is the direct, mechanical reason best-fit has a worse worst-case per-call cost than first-fit, independent of which one ends up leaving the free list in better shape afterward.

## E. OS/systems concepts touched

**25. Why does `FreeListAllocator`'s constructor over-allocate by exactly `kMaxSupportedAlignment` bytes rather than some other amount?**
That's the maximum possible distance between an arbitrary address returned by the underlying allocator and the next address that's a multiple of `kMaxSupportedAlignment` — in the worst case, the raw pointer is already `kMaxSupportedAlignment - 1` bytes past a boundary, needing almost a full alignment unit of padding to reach the next one. Over-allocating by any less could, in the worst case, leave no valid aligned starting point within the buffer at all.

**26. Does this allocator ever call `mmap`/`VirtualAlloc` directly, or interact with the OS's virtual memory system at all?**
No — both strategies get their backing storage from `std::make_unique<std::byte[]>`, which goes through the C++ runtime's allocator (`operator new[]`), which itself is typically backed by `malloc`, which for large requests often does call `mmap` internally — but that's a layer below anything this project's code touches directly. Everything in `ArenaAllocator`/`FreeListAllocator` operates purely on the resulting virtual addresses already handed to the process; there's no direct syscall usage anywhere in this codebase.

**27. Why might the "long-lived" workload show more page-fault-related timing noise than "short-lived" in the benchmark (as the README's methodology section describes)?**
The long-lived workload never frees anything mid-run, so by construction it touches new, never-before-written memory for essentially every allocation — each first touch of a fresh page can trigger a minor page fault (the OS mapping a physical page to satisfy the access) the first time. The short-lived workload, by contrast, frees and reuses the same small pool of memory repeatedly, so most of its pages are touched once early on and then simply reused — far fewer page faults overall, hence less of that particular source of per-call timing variance.

## F. Concurrency, correctness, and edge cases

**28. Is any part of this allocator thread-safe?**
No, by design and explicitly documented in the README "Limitations" — neither `ArenaAllocator` nor `FreeListAllocator` does any internal locking, so calling `allocate()`/`deallocate()` on the same instance from two threads concurrently is a data race (on `offset_` in the arena case, on the free list's linked-list pointers in the free-list case). `ENABLE_TSAN` exists and runs clean in CI, but that reflects the test suite's actual usage pattern (single-threaded), not a thread-safety guarantee under concurrent use.

**29. What happens if you call `deallocate()` on a pointer from a *different* `FreeListAllocator` instance?**
`owns()` checks whether the pointer falls within *this* instance's `[arena_base_ + sizeof(BlockHeader), arena_base_ + capacity_bytes_)` range; a pointer from a different instance's (different, unrelated) backing buffer essentially certainly fails that range check and returns `DeallocResult::NotOwned` immediately, never reaching the header-interpretation code at all. This is exactly what `InvalidPointerIsRejectedCleanly` tests, using a stack variable's address as the "foreign" pointer.

**30. Edge case: requesting an allocation exactly equal to `capacity_bytes_` (no room for any header/footer overhead)?**
It fails with `OutOfMemory` — the requested payload size plus `sizeof(BlockHeader)` plus `sizeof(BlockFooter)`, rounded up to the next 64-byte multiple, will always exceed `capacity_bytes_` in this scenario (since `capacity_bytes_` is itself already a multiple of 64 containing zero header/footer overhead budget), so `find_fit()` finds no block large enough. This is implicitly covered by `ExhaustionReportsOutOfMemoryThenRecoversAfterFree`, which exhausts a small 512-byte arena with a 400-byte request plus overhead.

**31. Edge case: what happens to `allocation_count_` across a `reset()` with live allocations outstanding?**
It's unconditionally zeroed, along with `bytes_in_use_` and the free list — `reset()`'s contract (documented in `AllocatorStrategy`) is "release every outstanding allocation at once," so any pointer a caller was still holding becomes silently invalid (not use-after-free-detected, just genuinely dangling) the instant `reset()` returns. This is a real sharp edge callers must respect; it's analogous to how `ArenaAllocator::reset()` behaves, and is exactly why `reset()` is documented as "releases every outstanding allocation."

**32. What would happen if two calls to `allocate()` raced on `FreeListAllocator::free_list_head_` without a lock (hypothetically)?**
Classic lost-update/corruption: both threads could read the same `free_list_head_` value, both proceed to use the same block, and both `free_list_remove()` calls would race on rewriting the same `prev_free`/`next_free` pointers — easily producing a free list with a cycle, a dangling node, or a node pointing to itself, any of which `check_invariants()` would very likely catch on the next debug-build mutation (but only after the damage, i.e. two allocators now both believing they own overlapping memory, was already done). This is precisely why the README states this allocator is thread-unsafe rather than "probably fine in practice."

## G. Testing, sanitizers, CI, and benchmarking

**33. Why does `test_property_bounds.cpp` use `std::mt19937` with a fixed seed instead of a random/time-based seed?**
A randomized test with a non-deterministic seed is, by definition, potentially flaky — a seed that happens to expose a real bug might only occur once in a thousand CI runs, making the failure nearly impossible to reproduce locally. A fixed seed (four of them, actually — two per fit policy) makes the test's behavior completely reproducible: if it fails, it fails the same way every single time, on every machine, which is what actually makes a property test *debuggable* rather than just occasionally alarming.

**34. Walk me through why the benchmark's "long-lived, Debug-build" result was misleading, step by step.**
`free_list_first_fit`/`allocate()` and `deallocate()` both end with `assert(check_invariants())`. In a Debug build (`CMAKE_BUILD_TYPE=Debug`, no `-DNDEBUG`), `assert` is active, so `check_invariants()` — an O(n) walk over every physical block in the arena — runs after every single allocate/deallocate call. The "long-lived" workload never frees anything mid-run, so the number of physical blocks (and thus the cost of that O(n) walk) grows roughly linearly with how far into the run you are, making total cost roughly O(n²) across the whole run. That's a real, measured 1000x-looking slowdown that has nothing to do with the free-list algorithm itself — switching to a Release build (`-DNDEBUG`, `assert` compiled to nothing) removed it entirely, confirmed by rerunning the exact same workload and seeing throughput jump back in line with the other strategies.

**35. How did you verify the Debug-vs-Release discrepancy wasn't itself a bug (e.g., different code paths)?**
By comparing the actual CMake-generated compile commands and confirming `NDEBUG` is the only difference affecting `assert()` between the two configurations (`CMakeLists.txt` doesn't branch any allocator logic on build type), then re-running the identical benchmark binary-built-from-identical-source twice (once Debug, once Release) and observing p50 latency was already consistent across all five allocators even in the "slow" Debug run — only the aggregate *throughput* number (which is what gets dragged down by O(n²) total work) looked anomalous, while p50 (which reflects a single typical call) did not. That consistency is what told me the algorithm was fine and the cost was coming from something *outside* the measured hot path's typical case.

**36. Why report p50/p99 latency AND aggregate throughput, instead of just one or the other?**
They answer different questions and can genuinely disagree, as this project's own data shows: throughput (`total_calls / total_wall_seconds`) answers "how much work got done," which a handful of extreme outliers (page faults, scheduler preemption) can drag down even if the typical call was fast; p50/p99 answer "how long did a typical/near-worst call actually take," which is far more stable run-to-run (confirmed: p50 stayed at 41-42ns for free-list across 3 repeated runs of the long-lived workload while throughput swung from 3.5M to 8.6M ops/sec). Reporting both, rather than picking one, is what let me catch and honestly describe that discrepancy instead of hiding it behind a single summary number.

**37. Why gate `ENABLE_ASAN` and `ENABLE_UBSAN` together instead of separately, unlike offering them as fully independent options?**
Both instrument different classes of bugs (memory errors vs. undefined behavior like signed overflow or misaligned access) but neither has a strong reason to be tested in true isolation for this project, and combining them (`-fsanitize=address,undefined`) means half as many separate build/test cycles for the same coverage versus running four separate matrix legs (ASan-only, UBSan-only, both, neither). `ENABLE_TSAN` is kept strictly separate because it's *mechanically incompatible* with ASan in the same binary (enforced by a `FATAL_ERROR` in `CMakeLists.txt`), not just a convenience choice.

## H. Real debugging stories from this build

**38. Tell me about a real bug you found in this project, not a hypothetical.**
The benchmark's `malloc`/`new` "currently reserved" bookkeeping was wrong on my first pass: the lambda I wrote only did `reserved += size` on allocation and never decremented it on free, so for any workload with frees (short-lived, mixed), the reported `peak_reserved_bytes` for `malloc_free`/`operator_new_delete` was actually the *cumulative total ever allocated*, not the true concurrently-live amount — while the free-list allocator's own `stats().bytes_in_use` genuinely does go up and down with frees. That made the peak-reserved comparison between malloc and the custom allocators silently apples-to-oranges, and it would have been very easy to miss, since the resulting number (a few megabytes) looked plausible on its own.

**39. How did you find and fix that benchmark bug?**
I noticed it while writing the README's benchmark-methodology section and cross-checking what each column was actually supposed to mean — `free_list`'s peak was reported as 2,112 bytes for the short-lived workload (correctly tiny, since blocks get freed and coalesced constantly) while `malloc_free`'s was reported as 2.7 million bytes for the *same* workload, which didn't make sense for two allocators replaying the identical allocation/free sequence. Re-reading the lambda in `bench_main.cpp` made the missing decrement obvious. The fix: track each live pointer's requested size in a `std::unordered_map<void*, std::size_t>` for both the `malloc`/`free` and `operator new`/`delete` paths, decrementing `reserved` and erasing the map entry inside the free lambda — giving malloc/new the same "true live bytes" semantics the free-list allocator already had natively via its own block bookkeeping.

**40. Were there any bugs the sanitizers caught that you had to fix?**
No — ASan+UBSan passed clean on the very first run against the full test suite, including the randomized property test and the double-free/invalid-pointer tests, which was genuinely the result I hoped for given how carefully `check_invariants()` was designed before most of the allocation/deallocation logic was finalized (see "What I learned" in the README), not a claim that the code was bug-free on the first attempt overall — the benchmark bug above was real and caught by manual review, just not by the sanitizers (it wasn't a memory-safety bug, it was a bookkeeping-logic bug in test/benchmark code, a category sanitizers don't target).

## I. Scaling and production follow-ups

**41. How would you make this allocator meaningfully faster?**
For `FreeListAllocator` specifically: replace the linked free list with a segregated/size-class structure (an array of free lists, one per size bucket) so `find_fit` for common sizes becomes O(1) instead of O(k) — this is exactly how most production general-purpose allocators (`tcmalloc`, `jemalloc`) actually work, and is listed under "Future work" in the README precisely because it's the natural next step rather than a hypothetical one.

**42. What would "production-ready" mean for this project?**
Thread safety (currently explicitly absent), a size-class strategy for the small-allocation overhead problem the benchmark data demonstrates, and almost certainly configurable corruption-handling policy (currently: detect and report via return value; a production hardened allocator might want an option to `abort()` immediately on detected corruption instead, since continuing after detected heap corruption elsewhere in a process is its own risk).

**43. How would this allocator behave under a workload with allocation sizes much larger than any I benchmarked (e.g., multi-megabyte objects)?**
Both strategies should handle it correctly (there's no size-based special-casing in either), but a single giant allocation in `FreeListAllocator` would consume (or badly fragment, if freed and not immediately coalesced with something similar-sized) a correspondingly large fraction of the arena — and `ArenaAllocator`'s complete inability to reclaim any individual allocation would be an even worse fit for that pattern than for the small/medium sizes actually benchmarked here. I did not measure this directly (my workloads cap around 4KB), which is a gap I'd close before making a real production recommendation either way.

## J. Tricky cross-questions (authorship / honesty checks)

**44. Did you write every line of this yourself?**
I made every real design decision here — the strategy/facade split, the boundary-tag approach, the `alignas`-based alignment-for-free trick, the pmr contract-translation boundary, the benchmark methodology including catching my own bookkeeping bug — and used an AI coding assistant as a tool for writing implementation code, the same way I'd use any other tool. **45. If I asked you to add a `realloc`-equivalent to `FreeListAllocator`, where would you start?**
I'd add `void* reallocate(void* ptr, size_t new_size, size_t alignment)` to `AllocatorStrategy`. The implementation would read the existing block's header to get its current `block_size`, and have three cases: if the new size still fits within the existing block (accounting for header/footer/alignment overhead), potentially shrink via `split_block()`-like logic and return the same pointer; if the immediately-next physical block is free and large enough to absorb the growth, extend in place by merging forward (very similar to the backward-coalescing logic `deallocate()` already has, just without actually freeing `ptr` first); otherwise, fall back to allocate-new + `memcpy` + `deallocate`-old, exactly like a naive `realloc`. The in-place-growth case is the only genuinely new logic; the rest reuses existing building blocks.

**46. What's the one thing in this codebase you'd most want to revisit if you had another week?**
Running the benchmark across a wider range of allocation sizes, including ones much smaller (to make the 64-byte-granularity overhead concrete in the data, not just in the arithmetic I show in the README) and much larger than what I tested, since right now the "this allocator is a poor fit for tiny or huge allocations" claims are backed by structural reasoning but not by dedicated benchmark runs targeting exactly those regimes.

## K. Final cheat-sheet — facts to have cold

1. Two strategies: `ArenaAllocator` (bump, O(1), no individual free) and `FreeListAllocator` (first-fit/best-fit, boundary-tag coalescing, splitting).
2. `FreeListAllocator::kMaxSupportedAlignment = 64` — the alignment cap; anything larger is rejected with `AllocResult::InvalidAlignment`, not silently violated.
3. `BlockHeader` is `alignas(64)`, which both aligns every block's address to 64 AND pads `sizeof(BlockHeader)` to a multiple of 64 — the mechanism that makes alignment "free" with zero per-allocation bookkeeping.
4. Every block has a `BlockHeader` (start) and `BlockFooter` (end) — the boundary tag — specifically so `prev_physical()` can walk backward for coalescing.
5. Magic numbers: `kAllocMagic = 0xA110CA11u`, `kFreeMagic = 0xF4EEF4EEu` — the double-free/corruption detection mechanism in `deallocate()`.
6. `AllocResult`/`DeallocResult` are returned by value, never thrown/aborted — the "safe diagnosis" mechanism the spec asked for.
7. `check_invariants()` is O(n) in physical block count, run via `assert()` after every mutation in Debug builds only (compiled out under `NDEBUG`/Release).
8. **The one real debugging story**: Debug-build `assert(check_invariants())` made `free_list_first_fit` look ~1000x slower than reality on the "long-lived" workload — O(n²) total cost from an O(n) check running after every call as physical block count grew. Fixed by benchmarking Release (`NDEBUG`), not Debug.
9. **The one real benchmark bug**: `malloc`/`new`'s "reserved" bookkeeping in `bench_main.cpp` only incremented, never decremented on free, making peak-reserved comparisons unfair until fixed with a `std::unordered_map<void*, size_t>` side table.
10. Measured p50 latency: ~41ns for both custom allocators vs ~83-84ns for malloc/new, consistent across all three workloads (the single most trustworthy number in the whole benchmark).
11. `MemoryAllocator` is the facade (owns `unique_ptr<AllocatorStrategy>`); `PmrAdapter` is the separate class bridging to `std::pmr::memory_resource` (must-throw contract vs never-throw contract).
12. 25 GoogleTest cases across 4 files, all passing under plain Debug, ASan+UBSan, and ThreadSanitizer.
13. The randomized property test (`test_property_bounds.cpp`) uses 4 fixed seeds (never time-based) across 5000 iterations each, specifically for reproducibility, not speed.
14. `ArenaAllocator`'s `deallocate()` is a documented no-op; only `reset()` reclaims space — demonstrated at the benchmark level by its peak-reserved-bytes ballooning on churn-heavy workloads.
15. Neither strategy is thread-safe; `ENABLE_TSAN` passes clean in CI because the test suite is single-threaded, not because of any synchronization in the allocator code.
